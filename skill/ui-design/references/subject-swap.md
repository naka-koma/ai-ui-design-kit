# Subject Swap

## 目的

製品名、ロゴ、コピーを無関係な製品へ交換したとき、UIがそのまま自然に成立するかを考える。製品固有の設計意図が必要な場所で、一般的なSaaS表現へ流れていないかを確認するレビューである。

「交換しても自然」だけで失敗としない。独創性の量を競うテストではない。

## 適用範囲

新しい主要画面、大きなリデザイン、ダッシュボード、主要ワークフロー、製品固有の体験で実施する。誤字修正、単独の余白調整などでは省略できる。ログイン、基本設定、単純フォームは標準的であることが適切な場合が多い。

## 手順

1. 対象画面の役割と、signatureが必要な理由を `docs/design/signature.md` や依頼から確認する。根拠がない場合は推定を明示する。
2. 名前・ロゴ・文面を無関係な製品へ置き換えた状態を想定する。文字量、データ形、画面機能は一定とし、コピー変更による崩れと混同しない。実ファイルを書き換える必要はない。
3. 次の「交換後にも残るもの」を確認し、具体例を記録する。
4. 判定と根拠、必要なら最小の改善案を記録する。

## 交換後にも残るもの

- 密度: 専門作業向けの一覧性や比較のしやすさ
- ナビゲーション: 製品の仕事に沿った移動・切替
- 面の表現: 素材感、境界、透過、レイヤー
- 階層: 主役となる情報と補助情報の関係
- モーション: 状態変化の意味や連続性
- 操作モデル: 比較、編集、探索などの進め方
- テーマ挙動: 配色だけでなくコントラストや質感の適応
- 構成: 製品の用途に対応した配置と視線の流れ

## 判定

| 判定 | 条件 | 例 |
| --- | --- | --- |
| PASS | コピーを交換しても、根拠のある製品固有の意図が構造や操作に残る | 時系列比較を中心にした分析画面で、比較・選択・密度が維持される |
| NEUTRAL | 汎用性が画面の役割に合っている | 標準的なログインや通知設定で予測しやすさを優先 |
| FAIL | signatureが必要な画面で、その意図が消え汎用構成に収束した | 比較中心の主要画面が、仕事と関係の薄いKPIカードと装飾的heroに置き換わる |

FAILは画面の役割と失われた意図を特定できる場合だけ。NEUTRALを減点しない。signatureが未定義ならその不確実性を記し、独創性を捏造してPASSにしない。

修正では失われた構成・密度・操作を戻す。奇抜な色、不要なアニメーション、特殊なフォーム操作を追加して点数を上げようとしない。Subject SwapのPASSはアクセシビリティや操作性の合格を意味しない。
