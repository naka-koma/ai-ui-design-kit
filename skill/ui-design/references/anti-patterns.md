# アンチパターンを判断に使う

アンチパターンは流行や部品を禁止する一覧ではない。画面の目的、情報の理解、操作の完遂、Product Signatureを損なう反復的な判断を見つけるために使う。発見したら「なぜ問題か」「誰のどの仕事を妨げるか」「何へ直すか」を説明する。

| 症状 | 起きる問題 | 判断の修正 |
| --- | --- | --- |
| 製品名を替えるだけのhero、KPIカード、装飾グラデーション | 主タスクや製品の仕事との関係がなく、主役が曖昧になる | 主要タスクとsignatureへの寄与を確認する |
| 全画面を広い余白と丸いカードへ正規化 | 比較や一覧に必要な密度・連続性を失う | 既存の密度・構成を支える仕事を調べる |
| 個性を出すための特殊フォームや強制モーション | 予測可能な操作を壊し、習熟コストを上げる | 標準操作を維持し、必要な場所の表現を見直す |
| 薄い小文字、色だけで階層や状態を表現 | 読み取り・識別が難しく、情報が抜け落ちる | 読める状態で配置・余白・ウェイト・ラベルを使う |
| 透過や写真の上で文字が背景に埋もれる | 背景次第で内容が読めず、行動できない | 不利な背景で検証し、安定した文字背景を設ける |
| アクセシビリティ設定を選ぶまで読めない | 既定表示の利用者を排除する | 既定表示を修正し、設定は追加の選択肢にする |
| WCAG合格だけで視覚レビューを終了 | 主タスクの優先順位、長文、実データでの理解を見落とす | 読みやすさ・階層・主タスクを別に確認する |
| 参考サイトの表層をそのまま写す | 画像では成立しても、用途・内容・操作が異なる | 観察を意図と仕組みに分解してから適用する |
| Setup時の無断リデザイン、Syncで設計文書を置換 | プロジェクトの決定を消し、更新の安全性を失う | 導入・共通更新・Design Auditを分ける |
| 文書に全token値を転記 | コードと文書がすぐ食い違う | 正本のコードへリンクし、意図だけ記録する |

カード、グラデーション、丸み、hero、モーション自体を禁止しない。目的・既存方針・使いやすさに根拠があるかで判断する。参考との違いが意図的なら、問題ではなく製品の判断として残す。
