# Visual Review

変更範囲に合わせて確認する。小修正では対象と周辺、主要画面では主タスク全体を見る。

1. 対象画面、利用者のタスク、保持するsignatureを確認する。
2. 実際に表示できる場合、代表的な広い幅・狭い幅、該当テーマ、長い内容、空・読み込み・エラー等の関連状態を確認する。
3. キーボードの到達性と順序、フォーカス、拡大・reflow、コントラストを確認する。自動検査があっても目視や操作確認の代わりにしない。
4. 操作の流れに触れる変更では、導線、待ち・進み具合、失敗と回復、空・読み込み中の状態を [ux-considerations](ux-considerations.md) の観点で確認する。固定要素、重ね表示、スクロール、キーボード、タッチに触れる変更は、実機での確認を依頼する。
5. [読みやすさ](readability.md) と [階層](visual-hierarchy.md) を個別に判定する。想定した読む順番、素材や色の役割、異なる構成間の一貫性を画面全体で確認し、対象ユーザー・目的・媒体への適合を根拠に評価する。
6. 主要画面・大幅な再設計では [Subject Swap](subject-swap.md) を実施する。NEUTRALは適切な結果として扱う。
7. 実装差分と意図の対応を見直し、問題を依頼範囲内で修正する。

## 報告形式

- 対象・確認した幅/テーマ/状態・実際に使った検証方法
- アクセシビリティ、読みやすさ、階層それぞれの結果と根拠
- 操作の流れを確認した場合は、その観点と結果。実機で確認していない項目は、未確認と書く
- Subject Swap: PASS / NEUTRAL / FAIL、または省略理由
- 保持したsignature、変更した表現、残る制約

表示環境がない場合はコードレビューとして報告し、視覚検証済みと書かない。Kit Syncだけの依頼でこのレビューやDesign Auditを自動的に始めない。
